# Candidate: the forge and the fleet — replicate the model, not the instance

**Claim (captain articulation, 2026-07-20, near-verbatim).** Build-fast,
break-fast, fix-fast is not tolerable for users. Therefore: the captain's own
instance is the forge, where breakage is the method; users never touch it.
The *model* replicates per use case — each deployment its own instance, own
canon overlay, own blast radius. This prevents single points of failure
across the board and bounds every outage to one deployment.

**Corollaries.**
- "Off the shelf" was the wrong bar for trust infrastructure; the right bar
  is audience graduation: solo → stewarded partner → stewarded client →
  (maybe never) stranger. Prerequisites are per-audience queues, not one
  list, and each audience's true list is only discoverable by that audience.
- Propagation is the new hard problem replication buys: the forge runs main;
  the fleet consumes ratified releases (epochs as release trains, adoption
  paced per instance). The promotion pipeline is the propagation channel.
  oddkit's knowledge_base overlay + governance-baseline fallback is the
  existing seam.
- Caveat kept honest: replication removes shared-runtime SPOF; the blueprint
  stays a shared upstream, so a bad ratified pattern propagates too — paced
  adoption is the damper.

**Evidence.** Forge-mode receipts: 2026-07-19/20 shift (five casualties in
the forge, zero user exposure, three canon promotions out). Replication
precedent in the portfolio: per-business automation instance already furthest
along (family business). Field precedent: translation methodology replicates
per language community over shared checking discipline — a decade of the
captain's prior domain. Single-articulation status flagged; sweep should test
against the rebuild-vs-modify tipping-point seed (held 2026-07-20) and
"bulldoze the house, keep the blueprint."
